# بروتوكول Codex 100/100

## الغرض

هذا البروتوكول يحكم علاقة العمل بين مالك المشروع، المبرمج المشارك، Claude، وCodex.

Claude يستخدم للتخطيط والمساعدة في التفكير والتنفيذ. Codex هو بوابة الاعتماد الفنية الصارمة. لا يبدأ العمل ولا يدمج إلا بقرار Codex بدرجة `100/100`.

## الصلاحيات

مالك المشروع:

- يعتمد الأولويات التجارية والمخرجات المطلوبة.
- يراجع خطة الأسبوع التي يعدها المبرمج قبل عرضها على Codex، ويعيدها للمبرمج للتعديل عند الحاجة.
- هو الطرف الوحيد المخول بعرض الخطط، التقارير اليومية، وPull Requests على Codex.
- يصدر إذن البدء للمبرمج بعد اعتماد Codex، ويصدر إذن الدمج بعد المراجعة النهائية.

المبرمج المشارك:

- يقرأ وثائق المرحلة قبل إعداد الخطة.
- يجهّز خطة الأسبوع كاملة مع Claude ويسلمها لمالك المشروع.
- يعدل الخطة بناء على ملاحظات مالك المشروع قبل أي عرض على Codex.
- يبرمج فقط بعد إذن صريح من مالك المشروع مبني على اعتماد Codex `100/100`.
- يلتزم بالاختبارات والتوثيق والتسليم اليومي.
- لا يخاطب Codex مباشرة، ولا يعتبر أي تواصل غير صادر من مالك المشروع اعتماداً رسمياً.

Claude:

- يساعد في صياغة الخطة، تقسيم المهام، وتحسين المنطق.
- لا يملك صلاحية اعتماد البدء أو الدمج.

Codex:

- يراجع الخطة قبل البدء.
- يراجع التغييرات اليومية.
- يراجع PR قبل الدمج.
- يرفض أي عمل فيه مخاطرة معمارية، أمنية، اختبارية، أو تشغيلية.

## القاعدة الصارمة

لا يوجد اعتماد جزئي. `99/100` تعني رفض. `92/100` تعني رفض. القبول الوحيد هو `100/100`.

لا يسمح بالآتي:

- بدء أسبوع جديد بدون خطة معتمدة من Codex.
- كتابة كود قبل اعتماد خطة الأسبوع.
- فتح PR إلى `main` قبل اعتماد Codex النهائي.
- دمج PR إلى `develop` أو `main` بدون اعتماد Codex `100/100`.
- تجاوز ملاحظة Critical لأي سبب. Critical يوقف العمل الجديد فوراً حتى الإغلاق.
- تجاوز ملاحظة High إلى يوم لاحق بدون موافقة صريحة من Codex موثقة في Sign-off أو transcript.
- اعتماد شفهي بديل عن وثيقة مراجعة Codex.
- اعتماد خطي أو شفهي من مالك المشروع بديل عن Codex. موافقة المالك لا تغني عن Sign-off Codex حتى لو وافق المالك صراحة.

## دورة اعتماد الأسبوع

1. تحضير خطة الأسبوع:
   المبرمج يجهز الخطة كاملة مع Claude في `docs/phase-N/week-N-plan.md`.

2. مراجعة مالك المشروع قبل Codex:
   المبرمج يسلم الخطة لمالك المشروع. مالك المشروع يراجع فنياً وتجارياً، ويعيدها للمبرمج للتعديل عند الحاجة. لا تعرض الخطة على Codex قبل اقتناع مالك المشروع.

3. عرض الخطة على Codex:
   مالك المشروع وحده يستخدم هذا الطلب:

   ```text
   راجع خطة المرحلة N الأسبوع N. قيّمها على 100. ارفض إن وجدت أي ثغرة معمارية أو أمنية أو اختبارية أو تشغيلية. لا تعتمدها إلا إذا كانت 100/100.
   ```

4. مراجعة Codex للخطة:
   يجب أن تشمل: المعمارية، الأمان، الأداء، عزل الفروع، الاختبارات، PDPL، وضوح التسليم.

5. التعديل والإعادة:
   كل ملاحظة تعالج داخل الخطة نفسها مع قسم `سجل التعديلات بعد مراجعة Codex`.

6. الإذن بالبدء:
   عند `100/100` فقط، ومع إذن صريح من مالك المشروع، ينشأ branch مستقل بصيغة:

   ```text
   feat/phase-N/week-N-short-name
   ```

7. المراجعة اليومية:
   نهاية كل يوم يرسل المبرمج diff مختصر، الاختبارات، والمخاطر المفتوحة إلى مالك المشروع. مالك المشروع وحده يعرض التقرير على Codex.

8. اعتماد نهاية الأسبوع:
   لا يغلق الأسبوع ولا يدمج PR إلا بعد اعتماد Codex النهائي `100/100` وإذن صريح من مالك المشروع.

## بوابات المراحل

المرحلة 1:

- لا تبدأ إلا بعد اعتماد خطة الأسبوع 1.
- لا تغلق إلا بعد Codex `100/100` على كامل المرحلة.
- لا تبدأ المرحلة 2 قبل Tag المرحلة 1 واعتمادها.

المرحلة 2:

- لا تبدأ قبل اكتمال المرحلة 1 بنسبة 100%.
- يجب توثيق أي مدخلات ناقصة في `docs/pending-decisions.md`.
- لا تبدأ المرحلة 3 قبل اعتماد المرحلة 2 بنسبة 100%.

المرحلة 3:

- لا تبدأ قبل اعتماد المرحلتين 1 و2.
- لا تسليم نهائي بدون اختبارات خضراء، توافق PDPL، وCodex `100/100`.

## سياسة الدمج

يجب ضبط GitHub Branch Protection يدوياً على `main` و`develop`:

- منع push مباشر.
- طلب Pull Request قبل الدمج.
- طلب مراجعة واحدة على الأقل من مالك المشروع.
- طلب نجاح CI قبل الدمج.
- منع الدمج إن كان branch غير محدث.
- منع bypass إن أمكن.

يجب أن تكون Status Checks الآتية مطلوبة في Branch Protection:

- `branch-naming`
- `required-files`
- `codex-gate`

أي دمج تم بدون هذه الشروط يعتبر تجاوزاً للحوكمة، حتى لو سمح GitHub به بسبب إعداد خاطئ. عند حدوث ذلك يفتح Incident في `docs/incidents/` ويوقف العمل حتى تصحيح الإعدادات.

## دليل Sign-off

اعتماد Codex الرسمي لا يثبت بمجرد كتابة `100/100` في ملف. يجب أن يحتوي كل اعتماد على:

- ملف Sign-off داخل `docs/signoffs/phase-N-week-N-codex-signoff.md`.
- Transcript كامل وغير معدل داخل `docs/signoffs/transcripts/`.
- SHA256 للـTranscript داخل ملف Sign-off.
- الحقل الفعلي: `- النتيجة النهائية: 100/100`.
- مربع Approved معلّم في سطر القرار الفعلي.

يفشل CI إذا غاب أي عنصر من هذه العناصر.
