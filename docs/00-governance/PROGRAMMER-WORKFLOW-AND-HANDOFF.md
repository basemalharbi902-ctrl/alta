# طريقة عمل المبرمج والاستلام

## المبدأ

المبرمج يبرمج. مالك المشروع يحدد الاتجاه والخطة مع Claude. Codex يراجع ويعتمد أو يرفض. لا يوجد دمج ولا بدء مرحلة إلا بالرجوع إلى Codex والحصول على `100/100`.

## قبل بدء أي أسبوع

مالك المشروع يجهز الخطة مع Claude، ثم يضعها في ملف Markdown داخل المشروع:

```text
docs/phase-N/week-N-plan.md
```

الخطة يجب أن تحتوي:

- أهداف الأسبوع.
- المهام اليومية.
- الجداول وMigrations المقترحة.
- Models وEnums وStates.
- Filament Resources وPages وWidgets.
- Services وActions وJobs وNotifications.
- الصلاحيات وPolicies.
- الاختبارات المطلوبة.
- مخاطر التنفيذ.
- مدخلات العميل الناقصة.
- أثر التغيير على المراحل السابقة واللاحقة.

مالك المشروع وحده يعرض الخطة على Codex. لا يسمح للمبرمج ببدء التطوير قبل اعتماد هذه الخطة من Codex بدرجة `100/100`.

## أثناء التنفيذ

كل يوم عمل يجب على المبرمج تسليم مراجعة يومية إلى مالك المشروع باستخدام قالب:

```text
docs/templates/DAILY-CODEX-REVIEW-TEMPLATE.md
```

المراجعة اليومية تشمل:

- ماذا تم اليوم.
- الملفات التي تغيرت.
- رابط commit أو branch.
- الاختبارات التي شغلت ونتيجتها.
- المشاكل والمخاطر.
- ما سيعمل عليه غداً.

مالك المشروع وحده يعرض المراجعة اليومية على Codex.

أي ملاحظة Critical من Codex تعالج قبل أي تطوير جديد ولا يجوز تأجيلها. أي ملاحظة High تعالج قبل الانتقال لمهمة جديدة إلا إذا وثق Codex قبول التأجيل.

## طريقة Branches

الفروع الرسمية:

- `main`: إنتاج فقط.
- `develop`: تجميع المراحل المعتمدة.
- `staging`: فرع نشر تجريبي إلزامي عند وجود بيئة Staging، ولا يستخدم كبديل عن `develop`.

فروع العمل:

```text
feat/phase-1/week-1-foundation-auth
feat/phase-1/week-2-question-bank
feat/phase-1/week-3-exam-engine-certificates-pwa
feat/phase-1/week-4-students-state-machine

```

## طريقة Pull Request

كل PR يجب أن يحتوي:

- وصف واضح للتغيير.
- رابط خطة الأسبوع المعتمدة.
- نسخة من نتيجة Codex على الخطة.
- قائمة الملفات المهمة.
- أوامر الاختبار ونتائجها.
- تقرير الاختبارات في `docs/phase-N/week-N-test-report.md`.
- Screenshots للواجهات عند وجود UI.
- Migration notes.
- Rollback notes.
- قائمة قرارات العميل المعلقة.
- طلب مراجعة نهائية من مالك المشروع، ومالك المشروع وحده يعرض PR على Codex.

لا يعتمد PR بدون تعبئة قالب `.github/pull_request_template.md`.

## تعريف التسليم المقبول

التسليم المقبول هو الذي يحقق كل ما يلي:

- الكود موجود على branch مستقل.
- الخطة الأسبوعية معتمدة مسبقاً من Codex.
- التغيير مطابق لوثيقة المرحلة.
- الاختبارات خضراء.
- لا توجد ملاحظات Critical أو High مفتوحة.
- التوثيق محدث.
- أي افتراض بسبب نقص معلومات العميل موثق في `docs/pending-decisions.md`.
- Codex أعطى `100/100` للتسليم النهائي.
- Sign-off وTranscript وSHA256 موجودة ومطابقة.

## تعريف الرفض

يرفض التسليم مباشرة إذا حدث أحد الآتي:

- بدأ المبرمج بدون خطة معتمدة.
- يوجد كود غير مغطى باختبارات في منطق حساس.
- يوجد تغيير في الصلاحيات بدون Policy واختبارات.
- يوجد Migration بلا rollback واضح.
- يوجد تسرب محتمل بين الفروع.
- يوجد كود يتجاوز PDPL أو يخزن بيانات حساسة بلا ضرورة.
- يوجد اعتماد على خدمة خارجية بدون Adapter أو fallback موثق.
- توجد ملاحظات Codex لم تغلق.
- درجة Codex أقل من `100/100`.

## الاستلام الأسبوعي

الاستلام يتم بهذا الترتيب:

1. المبرمج يرفع PR.
2. المبرمج يرفق تقرير الاختبارات.
3. مالك المشروع يطلب من Codex مراجعة PR.
4. المبرمج يعالج ملاحظات Codex.
5. يعاد العرض حتى `100/100`.
6. بعد الاعتماد فقط يسمح بالدمج إلى `develop`.
7. بعد نهاية المرحلة واعتمادها يسمح بالدمج إلى `main` وإصدار tag.

## الاستلام النهائي لكل مرحلة

المرحلة لا تغلق إلا بوجود:

- خطة كل أسبوع.
- اعتماد Codex لكل أسبوع.
- PRs مغلقة ومعتمدة.
- اختبارات كاملة.
- توثيق وتشغيل Staging.
- Demo مقبول من مالك المشروع.
- وثيقة Sign-off موقعة داخل `docs/signoffs`.
- Transcript كامل وغير معدل داخل `docs/signoffs/transcripts`.
- SHA256 مطابق بين Sign-off وTranscript.
